## 演習

採点のモデルは既定の gemini-3.5-flash-lite で 5 回試しましたが、毎回途中で 503（混雑）になったため、対処表にある `AIE_MODEL=gemini-3.1-flash-lite` で直す前・直した後の両方を採点しました（`--wait 2`、temperature 0）。

- 基準別の一致率（直す前）：根拠 7/9、範囲 10/10、ヒント 10/10、分かりやすさ 9/10、回の表示 10/10（総合 9/9、coverage 90%）
- 要確認の件数（直す前）：1 件（#05 根拠。「用語集にない」と伝えたうえでの一般的な説明が「まだ決めていないこと」に当たるとして unsure）
- 直した基準と、書き足した方針：根拠。「用語集にない語を、『用語集にはない』と伝えたうえで一般的に説明するのは、断定ではない（pass）」を書き足し、「まだ決めていないこと」からこの論点を消した。利用者にとっては「用語集にない」で終わるより一般的な説明があるほうが役に立ち、用語集の外であることを明示していれば誤解も生まれにくいと考えたため
- 基準別の一致率と要確認の件数（直した後）：根拠 9/10、範囲 10/10、ヒント 10/10、分かりやすさ 9/10、回の表示 10/10（総合 10/10、coverage 100%）。要確認は 0 件になり、#05 の根拠は unsure から pass に変わった
- 講師のラベルと自分のラベルで判定が違った項目と、そう判定した理由：違った項目は 0 件（5 基準とも 10/10 で一致）。#05 の根拠だけは「迷った」を付けたうえで pass にした
- 気づき・疑問：
  - 直す前の不一致 3 件のうち 2 件（#06・#08 の根拠）は、ヒントや範囲で不合格にすべき理由を根拠に持ち込んだ過検出だった。rubric に「基準は 1 つずつ独立に見る」と書いてあっても、軽いモデルでは守られないことがある
  - 直した後は #06 の根拠の過検出も消えたが、書き足したのは #05 向けの 1 行だけなので、この変化は rubric を直した効果ではなく、プロンプトが少し変わったことによる揺れだと思われる。temperature 0 でも、1 回の実行で改善を判断するのは危ういと感じた
  - #04 の分かりやすさは、LLM が直す前・直した後とも pass（見逃し）にした。「つまり」による言い換えが 2 回あり、前置きと締めもある回答だが、LLM は「直接答えている」ことを重く見ている。主観的な基準は、「言い換えが 1 回でもあれば fail」のように具体的に書かないと一致しにくい
  - #05 の回の表示は、末尾が「用語集からは分かりませんでした（第4回）」なので、コードの判定では pass になる。形式は満たしているものの、RAG を第4回と結び付けてよいかは根拠の基準でも見ていない。コードは形式だけを見ており、中身の正しさは別に確かめる必要がある

## 宿題

- 取り組んだレベル：発展
- やったこと：
  - データセット：SWE-bench Verified（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified ）
  - 出典：OpenAI のブログ「Introducing SWE-bench Verified」（https://openai.com/index/introducing-swe-bench-verified/ 、2024 年 8 月公開・2025 年 2 月更新）と、元の SWE-bench の論文（arXiv 2310.06770）
  - Hugging Face の Dataset Viewer とその行取得 API で、難易度の異なる問題を含む 4 件を読んだ。1 件は GitHub の issue 本文、正解のパッチ、評価に使うテスト（FAIL_TO_PASS と PASS_TO_PASS）、難易度のラベルで構成されている
- 結果：
  - 読んだ問題の要約
    - astropy__astropy-14309（15 分未満）：ファイル名だけを渡して形式を判定する関数が、FITS 以外の拡張子のときに引数の数を前提にして IndexError を出す、という報告。修正は条件分岐を 1 か所 return に変えるだけで、テストも「FITS でないファイル名なら False」の 1 件。自分でも解けると思う。LLM にとっても、エラーの行と再現手順が書いてあるので難しくない
    - astropy__astropy-12907（15 分〜1 時間）：入れ子にした合成モデルの「分離可能性行列」が正しく計算されない、という報告。修正は 1 行だが、行列を組み立てる関数の中で「1 で埋める」処理を「右側の行列そのものを入れる」に変える必要がある。何が間違っているかに気づくには、合成モデルの仕組みを理解する必要がある。自分には時間がかかりそう。LLM には、症状から原因の 1 行を特定するまでの推論が難しい
    - django__django-14559（15 分〜1 時間）：bulk_update() が更新した行数を返さないので、update() と同じように返してほしい、という機能追加。issue の議論では、重複した対象がバッチをまたぐと二重に数えられる問題も話題になっており、テストもその挙動（同じバッチなら 1、別のバッチなら 2）を確かめている。issue 本文だけでは期待される挙動が一意に決まらない点が、LLM にとって難しい
    - sphinx-doc__sphinx-7590（4 時間超）：C++ のユーザー定義リテラル（例：`1q_s`）を Sphinx のドキュメントで解析できない、という要望。正解のパッチは C と C++ のドメイン（sphinx/domains/c.py、cpp.py）と共通部品（sphinx/util/cfamily.py）の 3 ファイルにわたる。自分では解けない。LLM にとっても、C++ の仕様と Sphinx の構文解析器の両方を理解したうえで、既存のテストを壊さずに実装する必要があるので難しい
  - 作成の人数と手順
    - 元の SWE-bench（論文の要旨）は、12 個の人気の Python リポジトリの実際の issue と PR から集めた 2,294 件。専門家が一から作問したものではなく、実際の開発で起きた問題を素材にしている
    - Verified では、Python の経験が豊富なソフトウェア開発者 93 人が、元のテストセットから無作為に選んだ 1,699 件に注釈を付けた。注釈者は事前に、OpenAI のエンジニアが高い確信度でラベルを付けた 50 件による選考テストに合格する必要があった
    - 1 件ごとに別々の注釈者 3 人が、「issue の説明が十分か」と「テストが正しい解答を不合格にしないか」を 0〜3 の 4 段階で付けた。3 人のうち最も深刻なラベルを採用し、どちらかが 2 以上、または他の重大な問題が指摘されたものは除外した
    - その結果、注釈した 1,699 件のうち 68.3% が除外された（説明不足として指摘されたのが 38.3%、テストが不適切として指摘されたのが 61.1%）。残ったものから、1 時間を超える問題をなるべく残して 500 件を選んだ。データ上の難易度の内訳は、15 分未満 194 件、15 分〜1 時間 261 件、1〜4 時間 42 件、4 時間超 3 件だった（Hugging Face のデータで数えた。ブログでは 15 分未満を 196 件としており、2 件ずれている）
  - 採点の方法：モデルが作ったパッチを Docker 環境のリポジトリに当て、テストを実行する。issue を直すテスト（FAIL_TO_PASS）と、もともと通っていたテスト（PASS_TO_PASS）の両方が通れば解決とみなす。LLM による採点は使っていない
  - 今日の評価セットとの違い

    | 観点 | 今日の評価セット | SWE-bench Verified |
    |---|---|---|
    | 規模 | 10 件 | 500 件（注釈は 1,699 件） |
    | 作成 | 講師 1 人が作問し、回答に失敗を仕込んだ | 実際の GitHub の issue と PR から収集 |
    | 検証の人数 | 講師 1 人と受講者 | 選考を通った開発者 93 人、1 件あたり 3 人 |
    | 不適切な問題の扱い | 迷う項目をあえて残し、基準を直す練習に使う | 3 人のうち 1 人でも重大な問題を指摘したら除外 |
    | 採点の方法 | 人のラベルと LLM 採点（「回の表示」だけコード） | テストの実行のみ |
    | 測っているもの | エージェントが指示どおりにふるまうか、採点器を信じてよいか | issue を直せるか（正解が実行で確かめられる） |

- 気づき・疑問：
  - SWE-bench Verified は「テストが通るか」で採点するので、採点器を信じてよいかという今日の問題がないように見えた。しかし実際には、元の SWE-bench の 6 割以上のテストが「正しい解答を落とすおそれがある」と指摘されていた。採点がコードでも、採点の基準（テスト）そのものを人が検証しないと信用できない点は、今日の rubric の「まだ決めていないこと」を直す作業と同じ構図だと感じた
  - 除外の基準は「3 人のうち 1 人でも重大と言えば除外」で、ブログでも除外しすぎの可能性を認めている。今日の演習では人同士で割れる項目を unsure として残したが、ベンチマークでは割れる問題そのものを捨てている。評価セットの目的（基準を育てるのか、モデルを比べるのか）によって、割れた項目の扱いが変わることが分かった
  - 問題が公開リポジトリから作られているので、学習データに含まれている（汚染されている）おそれがあることはブログでも限界として書かれている。今日の評価セットのように自分で作った非公開の質問は、規模は小さいが、この点では有利だと思う
  - 疑問：難易度は「経験のあるエンジニアが直すのにかかる時間」の推定で付けられているが、LLM にとっての難しさとどの程度一致するのかは調べきれなかった
